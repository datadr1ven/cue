How sensing works

TPlus aims to notice launch milestones the way a careful viewer would: several imperfect cues, combined with judgment — not a single brittle detector. This page covers what runs today, what comes next, and how outside contributors can plug in.

How it works today

Primary path

  • A mission plan of expected milestones (from Launch Library 2 when available)
  • Optical character recognition (OCR) of the webcast’s T+ / hold clock
  • An alert when that clock reaches a planned milestone

Supporting signals

  • Speech-to-text phrase matches as corroboration
  • Simple on-screen text heuristics
  • Still frames attached to alerts (for context, not as proof)

Speech alone does not notify subscribers. The mission plan still controls what can go to the public feed.

Next: multiple supporting sensors

Rather than relying on the clock alone, the webcast can feed several independent sensors. Each contributes evidence — a label, time, and confidence — that can support or contradict a planned milestone:

  • Video classification — scenes such as pad hold, liftoff plume, stage separation, or landing
  • Audio classification — crowd reaction, callout energy, or engine character (in addition to speech-to-text)
  • Improved on-screen text readers — tighter than today’s heuristics
  • Other attributable public signals later, if they stay optional and clearly sourced

Intended fusion rule: several agreeing signals near a planned milestone → a confident alert; a single isolated flash → log it and stay quiet.

Contributing a sensor

Contributors who care about launch audio/video can add sensors — small detectors that emit evidence — without rebuilding alert delivery (Telegram, the public feed, or the cloud worker).

Good fits

  • Phrase or pattern packs mapped to milestone ids
  • Small classifiers (frame or audio in → label + confidence)
  • Offline scorers that evaluate saved webcasts
  • Stream-side workers that emit evidence records while a flight runs

Out of scope

  • Posting alerts directly to subscribers
  • Competing with OCR for mission-clock ownership
  • Scraping private or credentialed feeds
  • Claiming official telemetry or range status

A sensor should report evidence: what it thinks happened, when, how confident it is, and which sensor produced it. Alert fan-out stays with the TPlus operator path.

The evidence record format is not finalized. Until a versioned schema is published, the best starting point is a GitHub issue describing modality, target milestones, sample clips, and how you would run beside the live webcast consumer.

Design principles

  • Sensors emit evidence; they do not send subscriber alerts on their own
  • One authoritative mission clock; other sensors propose what happened, carefully
  • Sensors are optional — missing models or GPUs must not break the OCR path
  • Source attribution is fine; pretending to be the official range is not
